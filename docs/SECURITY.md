# Security model

Kubernanny runs with read access to most of your cluster and a few write verbs. This page is the threat model: what an attacker with each piece could do, and what keeps that small. It also says how to revoke a device and rotate the keys, how the image is built, and what the phone stores.

Other pages own the details: every permission and the Helm value that removes it is generated in [PERMISSIONS.md](PERMISSIONS.md); every port and outbound connection is in [IN-CLUSTER.md](IN-CLUSTER.md#network); how each channel is protected is in [COMMUNICATION.md](COMMUNICATION.md); the wire format is [PROTOCOL.md](PROTOCOL.md). To report a vulnerability, see [SECURITY.md](../SECURITY.md) at the repository root.

## Threats

| If someone gets… | They can | They cannot | Mitigation |
|---|---|---|---|
| **a device's private key** (lost, unlocked phone) | read the status, node and workload lists, events, logs of pods that currently have an issue; sync or refresh a broken Argo app; restart a currently broken workload; start a CNPG, Longhorn or Velero backup whose backup is overdue or failed; ask Flux, External Secrets, Infisical or cert-manager to reconcile or renew an object that has a problem; uncordon a node cordoned for over 30 minutes; delete finished pods of a namespace; create a pairing code and so pair a device of their own; **blind and lock out the owner**: switch notifications, any module or any action off, silence issues, start a 24 h maintenance window, revoke every other device; switch on a module that is off by default because it sends data out of the cluster (`vulnerabilities`, `image-updates`) | name any other target, restart healthy workloads, delete anything but the finished pods an issue lists, read Secrets, switch on anything the Helm values switched off, do any of the blinding changes unnoticed | actions bound to open issues; switching notifications, a module or an action off, switching on a module that sends data out, starting a maintenance window, silencing any warning or outage (and a silenced warning that becomes an outage notifies again), revoking a device and pairing a new one each send **one notification through your channels first**, naming the device, even with notifications off in the app or during maintenance (only `checks.disabled: [notifications]` in Helm silences them); every change is in the audit log with the device. On such a message you did not expect: **revoke that device** from another paired device (settings → Paired devices) or with `node dist/cli.js revoke <id>`, check the settings, and if it already revoked your devices, [rotate everything](#rotating-everything) |
| **a device's private key, with opt-in issue actions enabled** (`job-rerun`, `force-delete-terminating`, `argocd-terminate-op`, `pvc-expand`) | run a failed Job again (its CronJob's template or a copy of it: whatever that Job does, it does once more, e.g. send mails, charge, migrate); force-delete a pod stuck in Terminating whose node looks down (if the node is in fact alive, a StatefulSet pod can run twice and two writers share a volume); end an Argo CD sync that has run for over 30 minutes (half applied, the rest waits); grow an almost full volume by a quarter (it cannot be shrunk again, and costs storage) | any of it on an object no issue names, or more than once per tap; delete a running pod; shrink a volume | each only while the issue is open; confirmation dialogs name the risk; audit log with the device; **leave them off unless you need them** |
| **a device's private key, with the opt-in sync options enabled** (`argocd-sync-prune`, `argocd-sync-replace`) | sync an app that an issue or "Ready to sync" offers with prune, deleting the resources Argo CD lists as no longer in Git (a CronJob removed from the chart, but also anything someone removed from Git by mistake); after a sync Kubernetes refused, sync it with Replace, overwriting fields other managers set on the app's objects | prune anything the app's own status does not list, or a list other than the one confirmed; replace without a refused sync; `Force=true` (delete and recreate) or any sync option the app does not name itself, beyond `ServerSideApply=true` | only from a sync offer; prune lists every resource and asks twice, the agent compares the list with the Application right before the patch; the admission policy allows `prune` only while the stored status lists a resource to prune, and only these options; audit log names the options and resources; **leave them off unless you need them** |
| **a device's private key, with rollbacks enabled** (`actions.enabled: [argocd-rollback]`) | roll any manual-sync, single-source Argo CD app back to any of its recent deployed states (the last entries of its `status.history`, usually 10), whether or not anything is wrong with it: an older release with a known bug or vulnerability is back in the cluster until someone syncs again | roll back an app with automated sync or several sources, pick a revision that is not in the app's history, point the app at another repository, path or chart, prune, change sync options, roll the same app back more than once in 5 minutes, do it unnoticed | the action is off unless the chart opts in; every rollback sends **one notification through your channels first** (even with notifications off in the app or during maintenance) and is in the audit log with the device, the app and both revisions; the agent and the admission policy both accept only a revision from the app's own history; a sync in Argo CD (or of the newest commit) undoes it. **Leave it off unless you need it**, and switch it off in the app when you do not need it right now |
| **the agent's key** (Secret `kubernanny-identity`) | answer devices in the agent's place, if they also control the network path; read recorded requests | act as a device, read recorded answers | only readable with kubectl; rotate by deleting the Secret (all devices pair again) |
| **the device list** (Secret `kubernanny-devices`) | public keys and names; FCM tokens of devices with native push | anything in the cluster; read a push | a token alone sends no text of one's own (that takes the relay's Firebase service account), but anyone can register an agent id on a relay with push and send that token Kubernanny's generic alert ("New status from a cluster"), within the relay's per-token limit (30 an hour) and its other push budgets ([RELAY.md](RELAY.md#native-push)); such a push never opens and carries no marker. Silent status pushes to that token too (2 an hour, a budget of their own): they wake the app on iOS now and then, never open and show nothing |
| **a device's FCM token** (from the device list, a relay's memory) | with the Firebase service account of the app's project too: make that phone show a notification with any text, on Android (an FCM notification message, shown by the system) and on iOS (an APNs alert without `mutable-content`, shown without the extension) | read a Kubernanny push or forge one that opens (sealed for the push key, authenticated by the agent key); put the person's marker on their text (it never leaves the phone); trigger any action (a tap at most opens a cluster already in the app) | a push without your marker did not come from your cluster ([NOTIFICATIONS.md](NOTIFICATIONS.md#is-this-push-real)); turn push off for that device, or revoke it; tokens FCM reports as gone are forgotten |
| **the relay's Firebase service account** (the relay's operator, or whoever steals it) | make every phone whose token it knows show a notification with any text, on Android and on iOS: FCM and APNs offer no way to forbid that, by design | open sealed pushes or forge one that opens; show a real cluster's text; add the person's marker; trigger any action | the marker on every real push ([NOTIFICATIONS.md](NOTIFICATIONS.md#is-this-push-real)); keep it in a Secret; `RELAY_PUSH=off`; a relay of your own with your own Firebase project and app build removes the third party |
| **the pod's log** | a pairing code: expired after 60 min, single use; the agent's public key. The same code is in the `kubernanny.app/qr#…` link printed under the QR code | a credential | none needed |
| **the `kubernanny.app/qr#…` link** (the log's QR code as an image) | the same as the log: the pairing code, the agent's address and public key, while the code is valid; it also sits in the browser history of whoever opened it | anything after the code was used or expired. kubernanny.app (Cloudflare Pages) gets only the request for `/qr`: the link is in the fragment, which browsers never send, and the page sends no referrer, sets no cookie and runs no analytics | open it only on your own device; a used code is worth nothing |
| **a pairing code** | pair one device, once, within 60 min; it then shows in the device list, the log and as a notification | anything after the code was used | revoke the unknown device |
| **a pairing link** (anyone can make one: a website, a QR code, a message, another app; `kubernanny://pair?…` or the web UI's `#/pair?…`) | open the app's pairing page with an address, a relay and an agent key of their choice, for example the address of a cluster already in the app, their own relay and the key of a fake agent | pair without a tap; give a cluster already in the app another agent key, relay or device key unless the person explicitly chooses "Replace the key anyway" past a warning; reach the pairing page through a push | the pairing page connects only after a tap and shows name, address, relay and the agent key's fingerprint first, the same one the agent's log prints (`Agent key: …`): compare them. An entry with that address or name and another key is refused by default, with both fingerprints shown. Replacing removes the old push registration and the old device at the old agent (best effort) |
| **the agent's public key** (a pairing link, a QR code) | send pairing attempts, directly or through the relay: wrong ones get `429 PAIRING_RATE_LIMITED` past 5 per 10 minutes, and all strangers together share a small budget (about 7200 attempts an hour at most) | guess a code (31^10 codes, under 10^-11 per code's hour), burn the code, keep the owner from pairing (the right code is compared before any throttle), use up a paired device's budget | none needed |
| **the network path** (Wi-Fi, ingress, proxy, relay) | see sizes and timing; drop calls | read, change or replay calls; pose as the agent | end-to-end encryption with a pinned agent key |
| **the relay** (the public one, or yours if compromised: its operator, or whoever controls it) | see which agents are online, when and how much they are called, the IP addresses of agents and phones; tell kinds of calls apart by size; drop, delay or replay calls (replays are refused); hold the dead man's switch messages and send them early, late or not at all | read or change a call, an answer or a push, learn which device calls, pose as the agent, register in an agent's place, burn a pairing code, make the agent spend more than a direct caller could, make a phone believe all is fine | end-to-end encryption with the pinned agent key; details in [A hostile relay](#a-hostile-relay); run your own ([RELAY.md](RELAY.md#running-your-own)) or leave it off and stay in the VPN |
| **Google or Apple** (FCM, APNs) | that a phone gets Kubernanny pushes, when and how large; that it gets status pushes (background pushes of a few hundred bytes, about one an hour on quiet days, so that the phone has a widget); drop them | read them (sealed with HPKE for the phone's push key) | `notifications.appPush.enabled: false`, or simply do not switch push on |
| **a notification endpoint** (ntfy, a webhook, the service behind it) | read what you send there: the cluster name, issue titles and causes | anything in the cluster (the agent only sends) | `notifications.detail: minimal` sends only counts; self-host ntfy; webhook URLs in `notifications.existingSecret` |
| **the vulnerability database** (api.osv.dev, or a mirror you point at; only with `vulnerabilities` on) | see which component versions you run; show made-up advisories or hide real ones | trigger any action (vulnerability issues carry none), make the app open a site other than osv.dev | leave the module off (the default), or point `VULN_DB_URL` at a mirror of your own |
| **a container registry** (only with `image-updates` on) | see which images' repositories you run (not which tags), and when; claim newer tags that do not exist or hide real ones | trigger any action, learn the running tag or anything about the cluster | leave the module off (the default), or `checks.disabled: [image-updates]` |
| **the pod** (RCE in the agent) | everything the ServiceAccount can read ([PERMISSIONS.md](PERMISSIONS.md)), the agent key, the device list; restart any Deployment, StatefulSet or DaemonSet, start a plain sync or a refresh of any Argo CD Application (with `actions.enabled: [argocd-rollback]` also a sync of any manual-sync, single-source app to a revision from its history), create a plain CNPG Backup, a Longhorn snapshot and backup, a Velero backup labelled with a schedule (whose spec the policy cannot compare with the schedule: any namespaces, to the storage locations already configured), trigger any Flux, External Secrets or Infisical reconcile and any certificate renewal, uncordon any cordoned node, delete any finished pod. A Velero backup cannot carry hooks (the policy denies them). With the opt-in ones also: create a Job within the Pod Security Standards baseline profile (no host namespaces, host paths or ports, privileged containers, extra capabilities, unconfined seccomp or AppArmor, unsafe sysctls) but with any image and ServiceAccount of any namespace (the policy cannot compare the template with a CronJob: the reason `job-rerun` is opt-in), read any ConfigMap by name (`config-change-hint`), force-delete any terminating pod, end any running Argo CD operation, grow any PVC by up to half. The action permissions are cluster-wide, not bound to open issues once the agent's own code is bypassed. **Without the admission policy** (Kubernetes before 1.30, or `rbac.admissionPolicy.enabled: false`): also change anything else on those objects with the same `patch`, such as images, service accounts, host settings or an Application's source, which amounts to running code in other namespaces | read other Secrets, delete anything but pods, create pods or workloads (Jobs only with `job-rerun`), escalate via RBAC; with the admission policy: change any field of a workload but the restart annotation, an Application but `operation` and the refresh annotation, a node but `spec.unschedulable` from true to false, delete a pod that has not finished (nor is terminating, with `force-delete-terminating`), change a Flux, External Secrets or Infisical object beyond its reconcile annotation, a certificate's status beyond the `Issuing` condition, a PVC beyond growing its request | non-root (user and group 1000), read-only root FS, no capabilities, seccomp; the chart's ValidatingAdmissionPolicy (on by default whenever a write action is enabled, Kubernetes 1.30+) denies the ServiceAccount everything beyond what the actions change ([PERMISSIONS.md](PERMISSIONS.md#admission-policy)); `rbac.allowActions: false` for read-only |
| **any pod in the cluster** (an in-cluster HTTP service the agent reads: Prometheus, Alertmanager, Grafana, Loki, Gatus, Uptime Kuma, or a pod answering in their place) | show wrong findings in the app and in notifications: made-up issues, stats, alert names | crash the agent or blank the app (every answer is type-checked, cut to a length and to 50 issues per module; a run that fails is logged, never fatal), offer actions (such modules never carry one), mention people in a chat (Slack and Discord bodies are escaped, Discord with `allowed_mentions` off) | `checks.disabled` for the module; `networkPolicy.egress` limits what the agent reaches |
| **unauthenticated network access to the agent** (in the cluster, or through the ingress or the relay) | spend the handshake budget of its own source address, of all strangers together, or of its path (direct or relay) | lock out paired devices: direct and relayed calls have separate ceilings, every direct source address has its own bucket, and a share of the direct ceiling stays reserved for addresses that recently made an authenticated call. Behind an ingress all direct calls share the controller's address; the relay path then stays usable | the relay's own per-agent limits; a NetworkPolicy on port 8080 |
| **the metrics port** | the score, issue counts, module status | issue texts, names, logs | not on the ingress; NetworkPolicy |
| **the phone** (lost, or its storage read) | see [What is stored on the phone](#what-is-stored-on-the-phone) | | revoke the device |

**Keys.** Device and agent keys are X25519; every call is a Noise IK handshake (`Noise_IK_25519_ChaChaPoly_BLAKE2b`) on audited primitives (`@noble/*`), checked against libsodium's implementation and published test vectors. Pairing codes are compared in constant time.

**Content Security Policy.** No inline script and no eval run anywhere the app's code runs: the agent sends a CSP header with its web UI (`agent/src/security/http-security.ts`); the native apps' WebView, where no server sets one, gets a `<meta>` policy from `app/src/index.html`, whose `connect-src` allows `https:` and `http:` because the app talks to whatever agent address was paired (every such call is end-to-end encrypted with the pinned key); the demo host gets its headers from `app/src/demo-host/_headers`; the website allows only the hashes of the inline scripts its prerendering writes. Links an agent sends (component links, ingress hosts, the web pairing address) open only if they are `http(s)`. On Android, Capacitor adds its bridge as a document-start script where the WebView supports that and falls back to an inline script on older WebViews, which this policy blocks; the app then needs a current Android System WebView.

**No HSTS from the agent.** The agent speaks plain HTTP on port 8080 and never terminates TLS; it used to send `Strict-Transport-Security` when a request carried `X-Forwarded-Proto: https`, a header any caller can write. HSTS belongs on whatever terminates TLS: set it on the ingress (for ingress-nginx `nginx.ingress.kubernetes.io/hsts`, which is on by default with TLS).

**Logs of pods with an issue** are readable by every paired device. They can contain secrets your application logs. `rbac.allowActions: false` does not change that (reading a log is no write). If it matters, restrict who may use the app, or set `actions.disabled: [logs]`: the chart then grants no `pods/log` and the logs route answers 403. With the plain manifest (`deploy/install.yaml`), remove the `pods/log` rule and set `DISABLED_ACTIONS=logs`.

### A hostile relay

The relay is not trusted, but it is not powerless. What it sees is listed in [RELAY.md](RELAY.md#what-the-relay-sees-and-what-it-does-not): the agent id, when the agent is online, the IP addresses of agent and phone, and the timing and sizes of calls; never their content or which device calls. Beyond that it can:

- **Drop, delay or reorder calls**, or answer `RELAY_AGENT_OFFLINE` when the agent is online. The app then shows the agent as unreachable; in the VPN it goes direct. An answer it makes up does not come from the pinned agent and fails to open; the app shows that it was discarded.
- **Replay a call it carried.** The agent's replay cache refuses it until the request's clock window has passed (also for a request first refused because its time lay ahead), the clock window after that; a replayed request has no effect and its answer is useless without the device's ephemeral key.
- **See sizes and timing (a side channel).** Requests are the JSON `{m,p,t,b}` sealed with a fixed overhead (1 + 32 + 48 + 16 bytes), so their size follows the path: `GET /status` (about 140 bytes), the views (`/nodes`, `/workloads`, …), a log request or an action (`POST /actions/restart?issue=…`, longer, with the issue id) and a pairing attempt are told apart by length, roughly, not by content. Answers reveal the size of what came back: a short sealed refusal (`DEVICE_UNKNOWN`), a status with few or many issues, a log of a few KiB. Timing shows when the app is open (it polls every 30 s while in the foreground) and when someone acts. Padding would hide much of this: requests padded to one size (say 1 KiB) cost under 1 KiB per call; answers padded to power-of-two buckets cost up to twice the bytes. It would change the wire format and the test vectors, so it is not done in protocol version 1; timing would leak anyway.
- **Use the strangers' budget, never a device's.** Calls through the relay go through the same limits as direct calls ([PROTOCOL.md](PROTOCOL.md#what-the-agent-checks-in-order)): junk that fails the size, version or replay check costs nothing; opening a handshake has one generous ceiling for relayed calls (400, refilled at 200 per second), only as CPU protection; after the handshake each paired device spends its own budget, and unknown keys (pairing attempts included) share one small one (20, refilled at 2 per second). So a relay, or anyone sending through it, can use up the strangers' budget and slow other pairing attempts down, but cannot touch a paired device's budget; only a flood past the handshake ceiling (hundreds of valid-looking requests a second) delays everyone. The agent spends no more on a relay than on a direct caller: a relay message is at most one request (larger ones close the connection before they are buffered), the challenge is answered once per connection, cancels count only for calls in flight, at most 16 calls run at once, answers a relay does not read close the connection after 16 MiB queued, and a connection that drops right away does not reset the reconnect backoff.
- **Try pairing codes**, under the same rule as a direct caller: wrong codes never burn the code, the right one is compared before any throttle, and guessing is bounded by the strangers' budget ([PROTOCOL.md](PROTOCOL.md#pairing)).
- **Drop or delay pushes** (the agent counts the channel as failed and tries again next run) and learn their metadata: each phone's FCM token and platform, a push key id, size and time, and whether it is a status push (so which phones have a widget). It cannot make a push that opens: that needs the agent's private key.
- **Misuse the dead man's switch.** It holds each opted-in phone's FCM token and sealed "agent silent" message for up to 27 hours. It can send that message early (a false alarm that the agent is silent), late (within its validity) or not at all, and withhold the "reachable again" report, after which the agent says nothing. It cannot read or change a message, make one that opens, show one twice or one older than the last shown, show it when the phone heard from the agent within the grace, or make a phone believe all is fine: a deposited message only says "silent", and "reachable again" is sealed by the agent when it is back ([PROTOCOL.md](PROTOCOL.md#dead-mans-switch)). Switch it off per phone in the app, for the deployment (`notifications.appPush.deadman.enabled: false`) or on your own relay (`RELAY_DEADMAN=off`).

Anyone on the internet can also register agent ids of their own on a relay (20 per address), hold up to a quarter of its answer memory from one address for at most 15 s per answer, and with many addresses slow it down for everyone; they cannot take another agent's id, crash it with a malformed request, or fill it from one or two addresses ([RELAY.md](RELAY.md#limits-against-abuse)). Run your own relay if the metadata matters, or leave it off and stay in the VPN.

### Residual risks

No system is completely secure. These remain:

- **Requests are not forward-secret against the agent's key** ([PROTOCOL.md](PROTOCOL.md#limits-stated-plainly)). Answers are. Requests carry paths and action names, no cluster data.
- **Custom URL schemes can be claimed by other apps.** A malicious app registered for `kubernanny://` could receive the pairing link and pair itself; it would show in the device list and the log, and can be revoked. Verified app links will replace the scheme with the native apps.
- **Manual pairing without the QR code** trusts TLS (or the port-forward) once, to fetch the agent key. Compare the fingerprint with the log if in doubt.
- **The agent is exposed to whoever can reach it.** Authentication happens before anything is dispatched, but an agent reachable from the internet is still a target for the next bug in Node or the agent's own HTTP code. Prefer a VPN or the relay over a public ingress.
- **In-cluster hops to monitoring are plain HTTP** unless your CNI encrypts.
- **A stranger with the agent's public key can slow pairing down**: unknown keys share one small budget, so a flood of them delays other pairing attempts (`E2E_RATE_LIMITED`, the app retries). They can never burn the code or have the right code refused for their wrong ones, and paired devices are not affected.
- **Whoever holds the relay's Firebase service account can put a notification of their own on a registered phone**, on Android and on iOS (the row above). It never carries a real cluster's text or your sign; a relay of your own with your own Firebase project removes the third party, and not switching push on removes the risk.

## What is stored on the phone

| What | Where | Whoever reads it gets | They do not get | Mitigation |
|---|---|---|---|---|
| the cluster list | app preferences: UserDefaults / SharedPreferences, localStorage on the web | names, addresses, pinned agent keys, the relay; with push on, the FCM token it registered (see the FCM token row in [Threats](#threats)) | the device keys, the push keys and the marker (next rows): so no call to an agent, no push opened | revoke the device if the phone itself is lost |
| the device private keys, one per cluster | iOS Keychain and Android Keystore, marked "this device only": not synced through iCloud Keychain and not restored onto another phone from a backup | whoever extracts one from an unlocked phone: that device, until revoked (the first row in [Threats](#threats)) | anything after the device is revoked | revoke the device if the phone itself is lost |
| the push keys (one per cluster) and the push marker | the iOS shared keychain group, the Android Keystore-protected store | open pushes for that one cluster, recorded ones included; read the push marker kept next to it | act as the device, call the agent | a key of its own per cluster, not the device key; turning push off deletes it |
| the widget's list | the App Group / SharedPreferences ([below](#home-screen-widgets)) | per cluster: its name in the app, light, number of outages and warnings, time of the last check, the titles of its three worst problems | addresses, keys, causes, call an agent | switch the widget off per cluster or for all; the home screen shows the same anyway |
| device keys of the web UI | the browser profile (origin storage, guarded by the CSP) | the device keys of the clusters paired in that browser | anything after the device is revoked | revoke the device; prefer the app on shared computers |

### Home-screen widgets

The iOS and Android widgets ([ARCHITECTURE.md, Widgets](ARCHITECTURE.md#widgets)) never call an agent and hold no key. Per cluster the app stores for them only: its id in the app, the name you gave it (at most 64 characters), the light, the numbers of open outages and warnings, when the agent last checked, whether it is a demo cluster, and the titles of its three worst problems with their severity (at most 120 characters each; none with `notifications.detail: minimal` or when all is well). No address, key, cause or action. The titles name what the issue is about (a namespace and workload, a node, a host), like a notification with `detail: full`; on the iOS Lock Screen they are privacy-sensitive and hidden while the device is locked, and the Lock Screen accessories show only counts and the name. Anyone who sees the home screen sees what the widget shows; iOS StandBy (iOS 17 and later, while charging) can show it on a locked phone too.

Where: iOS, the App Group `group.app.kubernanny` (UserDefaults, readable by the app and its widget extension only); Android, the app's private SharedPreferences file `kubernanny_widget` (Android backups are off for the whole app). With push on, the iOS push extension and the Android messaging service write the state a push carries into an entry the app already stored; for that the push extension is in the App Group `group.app.kubernanny` as well as `group.app.kubernanny.push`, while the widget extension is not in the push group and cannot read push keys. Silent status pushes are opened by the iOS app itself in the background (`AppDelegate`, with the extension's code), which is why the app has the Background Modes capability "Remote notifications"; it does nothing else in the background.

Turning it off: per cluster in its settings ("Show this cluster on the home-screen widget"), for all clusters on the cluster list ("Home-screen widgets: Off"). Either removes the entries at once, before the switch returns, and nothing is written for them until switched on again, by the app or by a push. Removing a cluster removes its entry too. The web UI has no widgets.

## Revoking a device

In the app: cluster settings → Paired devices → Remove. Any paired device can revoke any other, including itself. Or in the pod:

```sh
kubectl -n kubernanny exec deploy/kubernanny -- node dist/cli.js devices
kubectl -n kubernanny exec deploy/kubernanny -- node dist/cli.js revoke <id>
```

The key is dead on the next call.

## Rotating everything

```sh
kubectl -n kubernanny delete secret kubernanny-identity kubernanny-devices
kubectl -n kubernanny rollout restart deploy/kubernanny
kubectl -n kubernanny logs deploy/kubernanny    # new key, new pairing code
```

All devices must pair again; the app reports the old agent key as no longer answering.

## Supply chain

One image, built by GitHub Actions from this repository (`Dockerfile`, multi-arch). Runtime dependencies (bundled into one file with esbuild, no `node_modules` in the image): `ws` (the relay connection), `qrcode`, and `@noble/curves`, `@noble/ciphers`, `@noble/hashes` (audited, pure JavaScript, pinned to exact versions) through the shared `protocol/` package. The web UI is built in the same pipeline and copied into the image; it loads no third-party resources at runtime (fonts are bundled).

Every published image carries a build provenance attestation and an SBOM, and is signed keyless with Sigstore by the workflow itself (no long-lived key exists). Verify before you deploy:

```sh
cosign verify ghcr.io/kubernanny/agent:<version> \
  --certificate-identity-regexp '^https://github\.com/kubernanny/kubernanny/\.github/workflows/ci\.yml@refs/(tags/v.*|heads/main)$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
docker buildx imagetools inspect ghcr.io/kubernanny/agent:<version> --format '{{ json .SBOM }}'
```

The identity is the workflow file and the ref it ran for: `…/ci.yml@refs/tags/v1.2.3` for a release, `…/ci.yml@refs/heads/main` for `edge`; nothing else in the repository can sign. The workflows run with read-only permissions except the jobs that publish, pin every third-party action by commit, check the kubeconform download against its checksum, and the image starts from a base pinned by digest, without npm or other package managers in the final stage.

The Helm chart in `oci://ghcr.io/kubernanny/charts/kubernanny` is signed the same way. CI also renders the chart with the switches (`checks.disabled`, `actions.disabled`, `rbac.allowActions`) and fails if a switched-off permission is still granted.

## Checklist for a new install

- [ ] Agent reachable only in the VPN/LAN (or no ingress at all and the relay, [RELAY.md](RELAY.md))
- [ ] `networkPolicy.enabled: true` with the right ingress-controller and monitoring namespaces
- [ ] Notifications over HTTPS; `notifications.detail: minimal` for public services
- [ ] `rbac.allowActions: false` if you only want to look; opt-in actions left out of `actions.enabled` unless you need them
- [ ] `actions.disabled: [logs]` if your applications may log secrets

## Security reviews

Before the first public release the agent and the app went through an independent security review with a penetration test, and the relay through that review, a second one and a re-review. What they found was fixed before release, among it: a silence could hide an issue that got worse (a silence now covers only the severity it was set for, and silencing a warning or an outage is announced); data from in-cluster services could pose as the agent's own text or crash a run; an Argo CD Application's status could point a restart elsewhere; strangers could lock out paired devices through the rate limits or block pairing with wrong codes; replay entries were written after the clock check; the agent sent HSTS on a header any caller writes; a pairing link could pair without a confirmation; pushes could be replayed; a fake agent could fill the relay's memory, and a relay could replay another relay's registration challenge (the measurements are in [RELAY.md](RELAY.md#limits-against-abuse)). The admission policies came out of the same review; tested against a real API server, they showed two bugs before release ([PERMISSIONS.md](PERMISSIONS.md#admission-policy)). Changing a setting that could blind the owner now sends a notification first. Regression tests for the findings that need a whole agent are in `agent/src/security-review.spec.ts`.
